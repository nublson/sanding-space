# 013 — Put the demo stage's morph on the site's ease-out curve

- **Status**: DONE (iPhone feel check pending)
- **Commit**: 7e5a7f9
- **Severity**: MEDIUM
- **Category**: Easing & duration
- **Estimated scope**: 1 file, about 10 lines added
- **Depends on**: 011 (it adds the `demo-stage` view transition class this plan targets)

## Problem

When an essay card opens into its essay (or back), the demo stage's box moves and grows through the browser's default `::view-transition-group` animation. The repo sets no timing for it, so it runs the browser default: **250ms on plain `ease`**. Measured in Chromium at 375px wide, the box goes from 343×171.5px at y=476 to 375×480px at y=304.

Everything else in the same transition uses the site's curve. The page crossfade uses `var(--ease-out)` (`cubic-bezier(0.23, 1, 0.32, 1)`, `src/app/globals.css:58`) over 200ms, and after plans 011 and 012 the stage's images do too. Plain `ease` is a weak curve that starts slowly. So the biggest moving thing on screen lags behind the page at the start, then lands about 50ms after the page has settled, and feels like a separate animation.

No CSS in the repo sets this today. The only rule that touches view transition groups is the reduced-motion override at `src/app/globals.css:608-617`.

## Target

```css
/* src/app/globals.css — target, added at the end of the .demo-stage block from plan 011 */
/*
 * The stage's box moves and grows on the site's ease-out, over 250 ms: it
 * answers a tap, so it starts fast, and it lands with the page fade.
 */
::view-transition-group(.demo-stage) {
  animation-duration: 250ms;
  animation-timing-function: var(--ease-out);
}
```

Values and why:

- **Curve**: `var(--ease-out)`, the existing token `cubic-bezier(0.23, 1, 0.32, 1)`. The audit's usual rule for on-screen movement is the strong ease-in-out `cubic-bezier(0.77, 0, 0.175, 1)`. It was rejected here on purpose: this morph starts only after a tap and a network round trip (about 330ms on the recorded iPhone). A curve that starts slowly adds more waiting at exactly the moment the reader is watching. Ease-out answers right away.
- **Duration**: 250ms, under the 300ms budget for UI motion, ending 50ms after the 200ms page fade-in, so the stage settles last.
- Set only `animation-duration` and `animation-timing-function`. Do **not** set the `animation` shorthand or `animation-name`: the group's keyframes (`-ua-view-transition-group-anim-<name>`) are generated by the browser per transition and must be kept.
- Reduced motion: already covered by the global rule at `src/app/globals.css:608-617` (`animation-duration: 0s !important` on `::view-transition-group(*)`), which wins over this rule. Add nothing.

## Repo conventions to follow

- The site styles view transitions by React View Transition Class, never by element name. The `demo-stage` class comes from `share="demo-stage"` on `<ViewTransition>` in `src/components/stage/live-thumbnail.tsx`, which plan 011 adds.
- The shell already sets group timing the same way, by property, in `::view-transition-group(.shell-close) { animation: none; }` (`src/app/globals.css:563-565`). This plan sets timing instead of disabling it.
- Keep the *why* comment above the rule.
